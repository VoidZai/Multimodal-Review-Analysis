# Milestone 7 — Fine-tuning data prep + go/no-go plan (E8, RQ3)

**Status:** M1, M2, M3, M4a, M4b, M5, M6 complete. M7 covers PLAN.md §3 **E8** and §10
(the fine-tuning plan) — it produces the *separate, larger* synthetic grounded-QA
training set, the measured hardware/base-model decision, the untuned baseline the tuned
model must beat, and the **pre-declared go/no-go rule**. It does **not** run a fine-tune:
execution is M8, second half.

**The claim this milestone is allowed to make:** *we have a training set, a measured
feasibility envelope, and a decision rule fixed in advance.* Any sentence implying a
fine-tuned model exists, or that fine-tuning helped, is false until M8 and must not be
written. The mid-progress report's fine-tuning section is a **plan with numbers behind
it**, which is exactly what §7 asks for ("plan only, no runs").

**Scope in:** a training-context sampler disjoint from CRAGB's gold evidence; teacher
generation of grounded, cited answers (distillation from the RQ1 "large" arm); deliberate
construction of correct-abstention examples; a quality filter built on the *validated*
half of the M4b judge; the leakage + near-duplicate guard and the train/val/probe split;
the local 4-bit inference client and a measured base-model shortlist on the real GPU; the
untuned base-model baseline on CRAGB; a QLoRA VRAM/time feasibility probe; the data
datasheet; `reports/finetune_plan_v1.md`; and notebook `10_finetune_dataprep.ipynb`.

**Scope out:** any LoRA training run that is not the 20-step feasibility probe; any change
to the retriever, the grounded-QA prompt, the answer-quality judge, or any M1–M6 result;
DPO/RLHF (PLAN.md §12); the retriever-fine-tune fallback (designed here as a *rule*, built
only if M8 triggers it); the demo (M9).

### Six facts about the current state that shape this milestone

1. **The GPU is 4 GB, not 8 GB.** PLAN.md §10 says "small local, 4-bit, fits 8 GB —
   Qwen2.5-3B-Instruct or Llama-3.2-3B-Instruct." The actual dev machine is an **RTX 3050
   Laptop with 4096 MiB VRAM** (`nvidia-smi`, confirmed; `environment.yml` already records
   it in the dense-retrieval note). A 3B in 4-bit is ~1.8–2.2 GB of weights *before*
   activations, KV cache, LoRA optimiser state and gradient checkpointing overhead at the
   ~1.5–2k-token sequence lengths this prompt produces. That is not obviously survivable
   at 4 GB, and it is not something to resolve by reading a blog post — T7.7/T7.9 measure
   it and the base model is chosen from the measurement. **Expect the answer to be a 1.5B
   (e.g. Qwen2.5-1.5B-Instruct), with the 3B kept as the stretch option.** Correcting
   §10's assumption with a measured number is itself a report-grade engineering finding.

2. **There are two Python environments and the fine-tuning work lives in the second one.**
   The conda env `cragb` has `torch 2.4.1+cpu` and no `transformers`. The venv at
   `C:\venv\cragb` (PLAN.md §14.1's MAX_PATH workaround) has `torch 2.6.0+cu124`,
   `transformers 5.14.1`, `sentence-transformers 5.6.0`, and `torch.cuda.is_available() ==
   True` on CUDA 12.4. `peft`, `bitsandbytes`, `accelerate`, `datasets`, `trl` are **all
   missing** from both. T7.7 installs them into `C:\venv\cragb` only — nothing in M1–M6
   may start depending on them.

3. **The leakage guard already exists — reuse it, and then notice what it cannot catch.**
   T2.10 shipped `cragb.bench.assemble.{normalize_question_text, compute_question_hash,
   build_leakage_manifest, check_no_leakage}`, `benchmark/cragb_v1_leakage_manifest.json`
   (60 hashes), and `tests/test_no_leakage.py` — whose docstring already names E8 as its
   caller. But it is **sha256 of normalised text: exact-match only.** A teacher-generated
   paraphrase ("Do these fit true to size?" vs CRAGB's "Do these run true to size?") sails
   straight through. T7.6 must add a near-duplicate layer on top, not replace the hash.

4. **Only *part* of the M4b judge is validated, and the filter must respect that.**
   `results/tables/judge_validation_v1.csv`: faithfulness **κ=0.597**, conciseness 0.321,
   completeness 0.243, correctness **κ=−0.151** (worse than chance). E8's "filter with the
   validated judge" therefore means **filter on faithfulness/grounding only**, with
   citation validity handled by the *deterministic* checker from T4a.4 rather than by an
   LLM. Filtering on the correctness score would be dressing an unvalidated instrument up
   as quality control.

5. **CRAGB has only 2 abstention questions — so abstention cannot be evaluated on CRAGB
   alone.** `cragb_v1.jsonl`: 60 questions, 11 authored negatives, but PLAN.md §14.2 found
   9 of those 11 turned out answerable, leaving `is_abstention: true` on exactly **2**.
   Since "correct abstention" is one of §10's three target behaviours *and* a go/no-go
   criterion, a rule written against n=2 is unmeasurable. T7.4 builds abstention examples
   deliberately, and T7.6 reserves a held-out **behaviour-probe split** so the go/no-go has
   real power. This is a live design consequence of a finding already logged, not a new
   worry.

6. **Free-tier throughput bounds the dataset size, so target the low end of §3 E8's
   "1–5k".** PLAN.md §14.5: 45 live Groq calls took ~5.5 real minutes with no 429s.
   ~500 generation calls is therefore ~60 minutes of wall clock and a real rate-limit risk
   at the top end. The plan targets **~500 contexts × 3 questions = ~1,500 raw positives +
   ~400 constructed abstentions → ~1,200–1,600 accepted examples after filtering**, every
   call cached and every stage resumable. 1,200 well-filtered examples train a LoRA
   perfectly well; 5,000 unfiltered ones do not train it better.

**Ordering:** T7.1 → T7.2 → T7.3 → T7.4 → T7.5 → T7.6 is a strict chain (each consumes the
last one's artifact). T7.7 → T7.9 is an independent chain that can run in parallel from day
one — **start T7.7 early**, because if 4 GB cannot hold a QLoRA step at all, the go/no-go
doc's fallback branch (fine-tune the retriever instead) becomes the main plan and T7.10
gets written differently. T7.8 needs T7.7. T7.10 needs everything. T7.11 is reporting.

Code is not written yet; this file is the task breakdown only.

## T7.1 — Training-example schema and prompt-format parity with inference

**Objective:** Fix the exact on-disk shape of a training example, and guarantee that the
prompt a fine-tuned model sees at *training* time is byte-identical in structure to the one
it sees at *inference* time. Train/serve prompt skew is the single most common way an SFT
run silently produces a model that scores worse than the base — it is worth a whole task to
make it structurally impossible rather than a convention someone remembers to follow. The
secondary objective is to put every knob in config so T7.3–T7.6 carry zero magic numbers.

**Artifact:**
- `src/cragb/finetune/schema.py` —
  - `TrainingExample` frozen dataclass: `example_id`, `category` (one of the 7
    `benchmark/taxonomy.md` types), `source_doc_ids: tuple[str, ...]`,
    `source_parent_asins: tuple[str, ...]`, `question`, `context_text`, `answer`,
    `cited_doc_ids: tuple[str, ...]`, `is_abstention: bool`, `provenance: dict`
    (teacher model, prompt version, generation timestamp, construction method), plus
    `to_dict()` / `from_dict()` round-tripping through JSONL.
  - `render_training_prompt(example) -> str` — **calls
    `cragb.generate.grounded_qa.render_prompt` and
    `cragb.generate.context_builder.build_context`**, not a reimplementation. Same
    `src/cragb/generate/prompts/grounded_qa_v1.md` template, same `$context_block` /
    `$question` substitution, same `has_photo: yes/no` excerpt rendering.
  - `to_chat_messages(example) -> list[dict]` — the `[{role: user, content: prompt},
    {role: assistant, content: answer}]` pair the SFT trainer consumes, so the chat
    template is applied in exactly one place.
- `configs/finetune.yaml` — `seed: 42`; paths block; `sampling` (n_contexts, k
  excerpts-per-context = **5, matching `configs/grounded_qa.yaml`'s `retrieval.k`**,
  per-category quotas, max_review_chars); `generation` (teacher provider/model/temperature/
  max_tokens, questions_per_context); `abstention` (target share, construction methods);
  `filter` (faithfulness threshold, citation-validity requirement); `split` (val fraction,
  probe size, grouping key, near-duplicate threshold).
- `tests/test_ft_schema.py`.

**Expected outputs:** `TrainingExample` round-trips through JSONL byte-stably; a rendered
training prompt for a hand-built example that a human can read and confirm looks exactly
like a `results/tables/grounded_qa_transcripts_v1.jsonl` prompt.

**Python packages:** stdlib (`dataclasses`, `json`, `hashlib`) + `pyyaml` — all already in
`environment.yml`. **Add nothing here.**

**Validation checks:** the parity test is the point — take a real row from
`results/tables/grounded_qa_transcripts_v1.jsonl`, rebuild it as a `TrainingExample`, and
assert `render_training_prompt(...)` is **character-for-character equal** to the prompt that
transcript was actually generated from (rebuilt via the same `render_prompt` path T5.4's
`build_messages_for_row` already uses). Also: `to_dict → from_dict` is an identity;
`is_abstention=True` with a non-empty `cited_doc_ids` raises (the §14.3 contradiction guard,
detected by **containment** of `ABSTENTION_TEXT`, not equality — that lesson is already
logged, do not re-earn it); an unknown `category` raises.

**How I verify it worked:** `pytest tests/test_ft_schema.py -q` passes, and the parity test
in particular — if it fails, every downstream example in this milestone is subtly wrong and
I stop here rather than generating 1,500 of them.

**Git commit message:** `feat(ft): training-example schema with inference prompt parity (E8)`

**Mid-progress report:** Indirect (infrastructure) — but "training prompts are rendered
through the *same* function as inference prompts, asserted char-for-char" is one sentence
worth having in the engineering/rigor section.

**Estimate:** 60–75 min.

## T7.2 — Training-context sampler, disjoint from CRAGB's gold evidence

**Objective:** Choose which corpus documents the training set is allowed to be built from,
and prove the choice excludes the evidence CRAGB is scored on. "Disjoint from CRAGB
questions" (§3 E8) is necessary but not sufficient — if training contexts are the *same
reviews* that CRAGB's `relevant_ids` point at, the tuned model has memorised the eval's
evidence even with different question wording.

**Artifact:**
- `src/cragb/finetune/sample_contexts.py` —
  - `cragb_evidence_doc_ids(entries) -> set[str]` — the union of every `relevant_ids` and
    `cited_doc_ids` across all 60 CRAGB entries (plus, for completeness, every doc id that
    appears in `benchmark/pools_v1.jsonl`, since the pools are what the labels were drawn
    from).
  - `sample_contexts(corpus, taxonomy, *, exclude_doc_ids, config) -> list[ContextGroup]` —
    groups **by `parent_asin`** (a context should read like reviews of one product, exactly
    as a retrieved context does), takes k=5 reviews per group, assigns each group a
    taxonomy category by the keyword profile already in `configs/taxonomy.yaml`, and
    stratifies group counts to the category mix in `benchmark/taxonomy.md`.
  - Deliberately over-samples image-bearing groups so `has_photo: yes` appears at a
    realistic-or-better rate (the prompt has a photo-citation rule the model should get
    practice on; M6 showed only ~13.5% of docs carry images).
- `data/finetune/contexts_v1.jsonl` — one row per context group.
- `data/finetune/contexts_v1_manifest.json` — **committed**: seed, corpus sha256, config
  hash, `n_groups`, per-category counts, `n_docs_excluded_as_cragb_evidence`,
  `n_parent_asins_excluded`, photo-bearing share.

**Expected outputs:** `python -m cragb.finetune.sample_contexts` writes both files and prints
a per-category table plus the exclusion count.

**Python packages:** `pandas`, `pyarrow`, `numpy`, `pyyaml`, `tqdm` — all present.

**Validation checks:** the intersection of sampled doc ids with `cragb_evidence_doc_ids()`
is **empty** (asserted, not printed); the intersection of sampled `parent_asin`s with
CRAGB-evidence `parent_asin`s is empty *or* the count is reported explicitly as a knowingly
accepted weaker guarantee — pick one and write down which; re-running with the same seed
produces a byte-identical file (seeded via `cragb.utils.seeds`); every group has exactly k
docs; per-category counts match the configured quotas within ±1; no group contains two
reviews by the same `user_id` (a shopper reviewing the same product twice is not two
independent pieces of evidence).

**How I verify it worked:** `pytest tests/test_sample_contexts.py -q` passes; then read
three sampled contexts end-to-end and confirm they read like a coherent set of reviews about
one product, and that their assigned category is the one I'd have picked by hand.

**Git commit message:** `feat(ft): stratified training-context sampler disjoint from CRAGB evidence (E8)`

**Mid-progress report:** **Yes** — the per-category composition table and the exclusion
counts are half of the training-data datasheet, and the disjointness guarantee is direct
evidence against PLAN.md §1.4 **risk F** (eval leakage).

**Estimate:** 75–90 min.

## T7.3 — Teacher generation: grounded, cited answers (distillation from the RQ1 large arm)

**Objective:** Turn each context group into ~3 (question → grounded, cited answer) pairs
using `openai/gpt-oss-120b` — the RQ1 "large" arm — as the teacher. This is *distillation*
in the §10 sense: the small local model is being taught the large model's grounding and
citation discipline, not new facts.

**Artifact:**
- `src/cragb/generate/prompts/finetune_gen_v1.md` — a **new, versioned** prompt that takes
  a context block and asks for N diverse questions of a given category, each with a
  grounded answer that obeys `grounded_qa_v1.md`'s citation rules, returned as a single
  JSON array. It must *restate* the citation rules rather than link to them, since the
  teacher only sees this prompt.
- `src/cragb/finetune/generate_pairs.py` —
  - `render_generation_prompt(context_group, category, n)`,
  - `parse_generated_pairs(raw) -> list[TrainingExample]` — strict JSON-array parsing with
    the same defensive shape as `cragb.eval.judge.parse_judge_response`,
  - `generate_all(contexts, client, config)` — **resumable**: reads any existing
    `raw_pairs_v1.jsonl`, skips contexts already done, appends. Uses
    `GroqClient.complete_with_usage` so tokens/latency land in
    `results/cache/api_calls_v1.jsonl` from the first call (PLAN.md §14.5's lesson, applied
    on day one), and `DiskCache` so a re-run costs nothing.
- `data/finetune/raw_pairs_v1.jsonl` (git-ignored; the manifest is what's committed).
- `results/tables/ft_generation_cost_v1.csv` — one row: n_calls, prompt/completion tokens,
  wall-clock, and $ via `cragb.eval.cost_model` at `configs/pricing.yaml` rates.
- `tests/test_generate_pairs.py`.

**Expected outputs:** ~1,500 raw positive examples; a printed progress/resume summary
(`contexts done X/Y, new calls N, cache hits M, 429s R`).

**Python packages:** `requests` (via the existing `GroqClient`), `tqdm`, `pandas`. **No new
dependency** — do not add the `groq` SDK (T2.2's reasoning, still valid).

**Validation checks:** parsing tests against a stubbed client — a well-formed JSON array
yields N examples; a response with prose wrapped around the array still parses; a truncated
array raises rather than silently yielding a partial example (the §14.6 `gemini-3.6-flash`
lesson: a *parseable-looking but cut-off* response is a distinct failure shape from an empty
one); every citation in a generated answer is a doc id that was actually in that context
(assert at parse time and **drop the pair** if not — do not wait for T7.5's filter to catch
fabrication that is cheap to catch here); questions within a context group are not near-
duplicates of each other (reuse `draft_questions.dedup_questions`' difflib approach at the
configured threshold). Interrupting the run mid-way and restarting produces the same file as
an uninterrupted run.

**How I verify it worked:** run against 5 contexts live first, read all ~15 pairs by hand,
and confirm the answers are actually grounded in *those* reviews rather than fluent generic
shopping advice; only then run the full sweep. Check
`results/cache/api_calls_v1.jsonl` grew by the expected number of rows with non-null token
counts.

**Git commit message:** `feat(ft): teacher generation of grounded cited QA pairs (E8)`

**Mid-progress report:** **Yes** — the dataset size, the teacher-model choice framed as
distillation, and the generation cost row all go into the fine-tuning-plan section.

**Estimate:** 90 min.

## T7.4 — Correct-abstention examples, constructed rather than hoped for

**Objective:** Build the abstention half of the training set deliberately. §10 names correct
abstention as a target behaviour, PLAN.md §14.2 showed that *authoring* unanswerable
questions by hand mostly fails (9 of 11 turned out answerable), and CRAGB retains only 2
abstention cases. Construction beats authoring here because the ground truth is
*structural*: if the context provably cannot answer the question, the correct answer is
exactly `ABSTENTION_TEXT` and nothing else.

**Artifact:**
- `src/cragb/finetune/abstentions.py` — three construction methods, each tagged in
  `provenance["method"]` so the datasheet can report the mix and M8 can slice by it:
  1. **`transplant`** — pair a question generated for context A with an unrelated context B
     (different `parent_asin`, different category). Guard: reject if any content word of the
     question appears in B's text above a configured overlap threshold, so an accidentally
     answerable transplant never becomes a mislabelled "must abstain".
  2. **`categorical_absence`** — questions asking for information categorically absent from
     *all* review text (internal QA rates, lab measurements, warranty terms, thread counts).
     PLAN.md §14.2 identified exactly which of these actually survived contact with real
     data (`fabric_quality_neg_000`, `defects_neg_000`) — build from that shape, not from
     the 9 that failed.
  3. **`evidence_stripped`** — take a positive pair and remove the specific reviews its
     answer cited from the context, leaving a topically-related but non-supporting context.
     This is the hardest and most valuable case: the context *looks* relevant.
  - `build_abstentions(positives, contexts, config) -> list[TrainingExample]` targeting the
    configured share (~25%, comparable to CRAGB's 11/60 negative design intent).
- `data/finetune/abstentions_v1.jsonl`.
- `tests/test_abstentions.py`.

**Expected outputs:** ~400 abstention examples with a printed per-method count.

**Python packages:** stdlib + `pandas`. No new dependency.

**Validation checks:** every produced example has `is_abstention=True`, `answer` containing
`ABSTENTION_TEXT` (containment, per §14.3), and **empty** `cited_doc_ids`; `transplant`
rejects a pairing whose question terms overlap the target context above threshold (test with
a deliberately-overlapping pair); `evidence_stripped` leaves at least one doc in the context
(an empty context is a different, degenerate case, not the one we're teaching); no abstention
example's context contains any doc that its source positive's answer cited; the per-method
mix matches config.

**How I verify it worked:** `pytest tests/test_abstentions.py -q` passes; then **hand-read 20
sampled abstention examples and try to answer each from its context myself.** If I can answer
even two of them, the construction is producing mislabels and I fix the overlap guard before
these enter training data — a false "must abstain" label teaches the model to refuse
answerable questions, which is a worse failure than the one being fixed.

**Git commit message:** `feat(ft): constructed correct-abstention training examples (E8)`

**Mid-progress report:** **Yes** — the three construction methods and *why* construction
beats authoring (with §14.2 as the evidence) is a strong, honest paragraph, and the
abstention share is a datasheet number.

**Estimate:** 60–75 min.

## T7.5 — Quality filter: the validated judge criterion + a deterministic citation check

**Objective:** Drop the examples that would teach the wrong thing, using only instruments
whose reliability has been measured. Report the yield honestly — a filter that accepts 98%
of its input is not filtering, and a filter that accepts 40% means the generator needs
fixing, not the filter.

**Artifact:**
- `src/cragb/finetune/filter_pairs.py` —
  - **Stage 1, deterministic and free:** reuse `cragb.eval.citation_validity` /
    `cragb.bench.reference_answers.extract_citations` — every cited id exists in the
    context, no fabricated ids, abstentions carry no citations, format compliance (one
    paragraph, no headings/JSON). Any failure here is a hard drop, no API call spent.
  - **Stage 2, judged:** `cragb.eval.judge.score_answer` on the survivors, **keeping only
    the `faithfulness` score** (κ=0.597, the only criterion above the 0.4 usability bar) and
    dropping below the configured threshold. `configs/finetune.yaml` must carry a comment
    stating that correctness (κ=−0.151), completeness (0.243) and conciseness (0.321) are
    *deliberately unused* here and why — otherwise a future reader assumes it was an
    oversight.
  - Abstentions bypass stage 2 (there is nothing to be faithful *to*); they get stage 1 plus
    T7.4's own structural guarantees.
- `data/finetune/filtered_pairs_v1.jsonl`.
- `results/tables/ft_filter_v1.csv` — the funnel: `n_raw`, `n_dropped_citation_invalid`,
  `n_dropped_format`, `n_dropped_low_faithfulness`, `n_accepted`, per-category and
  per-`is_abstention` breakdowns, plus the judge-call cost row.
- `tests/test_filter_pairs.py`.

**Expected outputs:** ~1,200–1,600 accepted examples and the funnel CSV.

**Python packages:** existing only (`pandas`, `requests` via `GroqClient`, `tqdm`).

**Validation checks:** a fabricated-citation example is dropped at stage 1 **without** an
API call (assert the stubbed client saw zero requests); a valid example with a stubbed
faithfulness of 2 is dropped and one with 5 is kept; abstentions never reach stage 2;
the funnel arithmetic closes exactly (`n_raw == sum of all drops + n_accepted` — assert it,
because a funnel that doesn't add up is the most quietly misleading table in a report);
re-running is a full cache hit and costs nothing.

**How I verify it worked:** `pytest tests/test_filter_pairs.py -q` passes; then read 10
examples the judge dropped and 10 it kept and confirm I'd have made the same call. If the
accept rate is above ~95% I check whether the threshold is doing anything at all; if it's
below ~60% I look at the generation prompt before I look at the filter.

**Git commit message:** `feat(ft): judge-filtered training pairs with drop-reason funnel (E8)`

**Mid-progress report:** **Yes** — the funnel table is a real result, and "we filtered on the
one judge criterion whose κ cleared 0.4, and said so" is exactly the statistical-rigor signal
PLAN.md §11 item 3 is after.

**Estimate:** 75–90 min.

## T7.6 — Leakage guard, near-duplicate guard, and the train / val / probe split

**Objective:** Prove no CRAGB evaluation question — or a paraphrase of one — is in the
training data, and split what remains so that neither the val set nor the behaviour-probe
set shares a product with train. This is the task that makes every RQ3 number in the second
half believable.

**Artifact:**
- `src/cragb/finetune/split.py` —
  - `guard_leakage(examples) -> LeakageReport` — calls the **existing**
    `cragb.bench.assemble.check_no_leakage` against
    `benchmark/cragb_v1_leakage_manifest.json` (exact-hash layer), then adds the
    **near-duplicate layer** the hash cannot see: difflib ratio against all 60 CRAGB
    questions at the configured threshold, and — since `C:\venv\cragb` already has
    `sentence-transformers 5.6.0` and the M3 `bge-small` index — an embedding-cosine check
    as the semantic backstop for paraphrases that share no surface form. Drop, don't warn.
  - `split_examples(examples, config)` → **three** files, grouped by `parent_asin` so no
    product straddles a split:
    - `data/finetune/train.jsonl`
    - `data/finetune/val.jsonl` (~10%, for early stopping on val loss per §10)
    - `data/finetune/probe.jsonl` — a **balanced behaviour-probe set** (~40 answerable + ~40
      abstention, stratified by category), held out entirely. This exists because fact #5
      above makes CRAGB's n=2 abstention cases unable to support a go/no-go rule; the probe
      is what T7.10's rule is actually written against.
- `data/finetune/split_manifest_v1.json` — **committed**: counts, per-category and
  per-`is_abstention` balance per split, `n_dropped_exact_leak`,
  `n_dropped_near_duplicate` with the offending pairs listed, seed, and the parent_asin
  disjointness confirmation.
- `tests/test_ft_split.py`.

**Expected outputs:** the three JSONL files plus the manifest; a printed leakage summary that
should read `exact leaks: 0`.

**Python packages:** `difflib` (stdlib), `pandas`, `numpy`; `sentence-transformers` for the
embedding backstop — **already installed in `C:\venv\cragb`**, so this step runs there (or
degrades gracefully to difflib-only in the conda env, with the degradation recorded in the
manifest rather than silently skipped).

**Validation checks:** injecting a verbatim CRAGB question into the input is caught by the
exact layer; injecting a hand-written paraphrase of a CRAGB question is caught by the
near-duplicate layer (this test is the whole point of the task — write it first); the
`parent_asin` sets of train, val and probe are pairwise disjoint; the probe set's
answerable/abstention balance is within ±2 of target; splits are reproducible under the
seed; `train + val + probe + dropped == input` (arithmetic closes).

**How I verify it worked:** `pytest tests/test_ft_split.py -q` passes; then grep the three
output files for a distinctive phrase from two CRAGB questions and confirm zero hits; and
confirm `tests/test_no_leakage.py` still passes untouched (M7 must not modify the M2 guard,
only call it).

**Git commit message:** `feat(ft): leakage + near-duplicate guard and grouped train/val/probe split (E8)`

**Mid-progress report:** **Yes, strongly** — this is the direct answer to "how do you know
your fine-tuning data doesn't leak your benchmark," and the near-duplicate finding (whatever
its count) is a concrete rigor artifact. PLAN.md §1.4 risk F closes here.

**Estimate:** 60–75 min.

## T7.7 — Local 4-bit inference client and a *measured* base-model shortlist

**Objective:** Replace PLAN.md §10's 8 GB assumption with numbers from this machine, and give
the project the one capability it lacks — running a local model behind the same interface

- `results/tables/ft_base_baseline_v1.csv` — format compliance, citation validity,

**Expected outputs:** the baseline CSV plus 3–5 transcripts worth quoting.

## T7.9 — QLoRA feasibility probe: does a training step fit in 4 GB, and how long is an epoch?

**Objective:** Answer the two questions the go/no-go's "within T hours of GPU time" clause
depends on: (1) does a QLoRA step at the real sequence length fit in 4 GB, and (2) how long
does one epoch over `train.jsonl` actually take? Twenty steps of measurement now prevents a
second-half milestone that discovers on day one that it cannot run.

**Artifact:**
- `src/cragb/finetune/train_lora.py` — written now, run only as a probe: config-driven
  QLoRA setup (4-bit base, LoRA on attention + MLP projections, gradient checkpointing,
  batch size 1 + gradient accumulation, `max_seq_len` set from the **measured** p95 token
  length of rendered training prompts, not a guess), a `--probe-steps N` flag, and per-step
  peak-VRAM / seconds-per-step logging. `configs/finetune_train.yaml` carries the
  hyperparameters as **placeholders explicitly marked "set in M8 from T7.8's failure
  modes"** — PLAN.md §10 is deliberate about not inventing final values here, and the config
  should say so in a comment rather than looking authoritative.
- `results/tables/ft_qlora_probe_v1.csv` — per configuration (model × LoRA rank ×
  max_seq_len): peak VRAM, s/step, OOM yes/no, and extrapolated minutes/epoch over the real
  train-set size.
- A short prompt-length distribution figure or table (p50/p95/max tokens over
  `train.jsonl` rendered through `render_training_prompt`) — this is what sets `max_seq_len`.

**Expected outputs:** the probe CSV; a stated, defensible `T` (hours of GPU time for the M8
pilot run) and the largest configuration that fits.

**Python packages:** `peft`, `trl`, `datasets`, `accelerate`, `bitsandbytes`, `transformers`,
`torch` — installed in T7.7, run from `C:\venv\cragb`.

**Validation checks:** the probe overfits a **single** example to near-zero loss in ~20 steps
(the standard sanity check — if loss doesn't fall on one example, the data collator, label
masking, or chat template is wrong, and finding that now is worth the whole task); **loss is
computed on completion tokens only**, with the prompt masked out (assert the label tensor
has `-100` over the prompt span — an unmasked prompt trains the model to generate review
contexts, which is not the objective); peak VRAM is read from
`torch.cuda.max_memory_allocated()`; an OOM is caught and recorded as a row, not a crash.

**How I verify it worked:** watch the 20-step loss curve fall on the single-example overfit;
confirm the label-mask assertion passes; then read the extrapolated epoch time and decide
whether M8 is a weekend or an afternoon. If **every** configuration OOMs, that is the
fallback trigger and I write T7.10's retriever-fine-tune branch as the primary plan — a
clean, evidence-backed pivot, not a failure.

**Git commit message:** `feat(ft): QLoRA feasibility probe — VRAM, step time, epoch budget (E8, §10)`

**Mid-progress report:** **Yes** — "one epoch is N minutes at rank R and seq length L on 4 GB"
is what makes the plan credible rather than aspirational, and the label-masking sanity check
is a nice methodological detail.

**Estimate:** 75–90 min.

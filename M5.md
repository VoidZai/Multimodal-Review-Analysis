# Milestone 5 — Cost & latency (E6, Goal G4)

**Status:** M1, M2, M3, M4a, M4b complete. This milestone covers PLAN.md §3 E6 / §8 G4 —
quantifying the *operational* cost of every configuration already built, then joining it
to the quality numbers M4b produced so the "is the big model worth it?" question becomes
a decision artefact rather than an opinion (PLAN.md §11 upgrade #5).

**Scope in:** index build time & on-disk size; retrieval QPS and p50/p95 latency
(BM25 vs dense); end-to-end per-question latency for the three answer arms
(closed-book, RAG-small, RAG-large); token accounting and $/query; peak RAM/VRAM;
the joined quality-vs-cost table and the Pareto scatter (report figure #4).

**Scope out:** the multimodal pilot (M6), fine-tuning data prep (M7), and any *new*
quality measurement — M5 consumes `results/tables/rq0_answer_quality_v1.csv` and
`rq1_answer_quality_v1.csv` as given.

**Two facts about the existing codebase that shape this milestone:**

1. `GroqClient.complete()` returns only the completion *string* — the API's `usage`
   block (prompt/completion token counts) is discarded, and `DiskCache` stores only that
   string. So **none of the 180 transcripts already generated in T4b.2 carry token
   counts**, and re-reading the cache cannot recover them. T5.2 fixes this going forward
   *without* changing the cache key (the payload must stay byte-identical or every
   existing cached response becomes a miss and re-spends free-tier quota — see
   `configs/grounded_qa.yaml`'s `reasoning_effort` comment for the same hazard).
2. A cached call has ~0 ms latency and $0 cost. Every *timing* number in this milestone
   must therefore come from a **deliberately cache-bypassed run**, and must say so in the
   artefact. This is the central methodological point of M5 — get it wrong and the Pareto
   plot claims the 120B model is free.

Tasks are linear except the retrieval side (T5.3) and the generation side (T5.2, T5.4),
which are independent of each other and can be built in either order.

Code is not written yet; this file is the task breakdown only.

## T5.1 — Timing/resource measurement primitives

**Objective:** One correct, tested place for "how long did this take" and "how much
memory did it use", so no experiment hand-rolls `time.time()` deltas with a different
clock, a different warm-up policy, or a different percentile convention. PLAN.md §5
already lists `utils/timing.py` in the intended tree; it is the one module never built.

**Artifact:**
- `src/cragb/utils/timing.py` + `tests/test_timing.py` —
  - `Timer` context manager using `time.perf_counter()` (monotonic; `time.time()` is
    wall-clock and can jump on an NTP adjustment),
  - `time_calls(fn, args_list, repeats, warmup) -> list[float]` (per-call seconds, with
    the warm-up iterations discarded, not averaged in),
  - `latency_stats(seconds) -> dict` with `n, mean, p50, p90, p95, min, max, qps`
    (`qps = n / total_seconds`, documented as *sequential single-client* throughput —
    not concurrent QPS),
  - `peak_memory() -> dict` with `rss_mb` (`psutil.Process().memory_info().rss`) and
    `vram_mb` (`torch.cuda.max_memory_allocated()` when CUDA is available, else `None`).

**Expected outputs:** importable module; `latency_stats` on a known list returns
hand-checkable percentiles.

**Python packages:** `psutil` (already installed), `torch` (already in the `C:\venv\cragb`
short-path venv, PLAN.md §14.1) — import it lazily inside `peak_memory` so the module
still imports in the base env with no CUDA.

**Validation checks:** unit tests — percentile of a fixed list `[1..100]` matches the
expected value under a stated interpolation convention; warm-up calls are genuinely
excluded (count the returned durations, don't just eyeball the mean); `peak_memory`
returns `vram_mb=None` rather than raising when torch/CUDA is absent; `Timer` records a
duration even when the wrapped block raises.

**How I verify it worked:** `pytest tests/test_timing.py -q` passes.

**Git commit message:** `feat(utils): timing + resource-measurement primitives (G4)`

**Mid-progress report:** Indirect (infrastructure; every M5 number flows through it).

## T5.2 — Token + latency telemetry on the API client

**Objective:** Capture what the API already tells us and we currently throw away:
`usage.prompt_tokens`, `usage.completion_tokens`, the model id, the measured round-trip
latency — plus whether the call was a **cache hit or a live call**, which is the flag
every later cost/latency number depends on.

**Artifact:**
- `src/cragb/generate/api_clients.py` — add `complete_with_usage(messages) ->
  CompletionResult(text, prompt_tokens, completion_tokens, latency_s, cached, model)`.
  `complete()` stays as-is and delegates, so **no existing caller changes** and the
  request payload (hence the cache key) is untouched.
- Extend `DiskCache` to write a sidecar `*.meta.json` next to each cached response
  holding the usage block, so a cache hit can still report token counts (only latency and
  cost are unrecoverable for a hit). Entries written before this task have no sidecar and
  must return `None` token counts, not crash.
- Append-only call log at `results/cache/api_calls_v1.jsonl` (one row per call: timestamp,
  model, tokens, latency, cached) — the raw material for T5.4.
- `tests/test_api_clients.py` / `tests/test_api_cache.py` extended.

**Expected outputs:** module importable; a fake-transport unit test showing a live call
records tokens + latency and that a repeat of the same call reports `cached=True`.

**Python packages:** none new.

**Validation checks:** the cache key for an unchanged payload is **byte-identical to
before this task** (assert against a hash hard-coded from the current implementation —
this is the regression that would silently re-spend quota); a cache entry written before
this task (no sidecar) still loads; `complete()`'s return type and value are unchanged.

**How I verify it worked:** `pytest tests/test_api_clients.py tests/test_api_cache.py -q`;
then re-run one already-answered T4b.2 question and confirm **zero new response files**
appear in `results/cache/api`.

**Git commit message:** `feat(generate): token + latency telemetry on Groq client (G4)`

**Mid-progress report:** Indirect (enables the $/query table).

## T5.3 — Retrieval cost/latency harness: build time, index size, QPS, p50/p95

**Objective:** The retrieval half of G4, for both arms of RQ2.
`results/tables/retrieval_index_build_v1.json` already records `build_seconds` and
`device` from T3.5 but **not index size on disk, not search latency, and not memory** —
this task completes it.

**Artifact:**
- `configs/cost_latency.yaml` — measurement knobs in one place: `n_query_repeats`,
  `n_warmup`, `k`, which retrievers, corpus path, output paths. No magic numbers in code
  (PLAN.md §5).
- `src/cragb/eval/cost_latency_retrieval.py` + `tests/test_cost_latency_retrieval.py` —
  builds each retriever under `Timer`, measures serialized index size in bytes, then
  times `search(q, k)` over **all 60 CRAGB questions × N repeats** with warm-up discarded,
  via T5.1's helpers.
- `results/tables/retrieval_cost_latency_v1.csv` — one row per retriever:
  `retriever, n_chunks, build_seconds, index_bytes, peak_rss_mb, peak_vram_mb, device,
  n_queries, qps, latency_p50_ms, latency_p90_ms, latency_p95_ms, latency_mean_ms`.

**Expected outputs:** two rows (bm25, dense) with plausible physics — dense build is ~90×
slower than BM25 per the existing build report (459.8 s vs 5.0 s), and dense search
should be the slower of the two per query on CPU.

**Python packages:** `numpy`, `pandas` (present); `sentence-transformers` / `torch` for
the dense arm — **run this task inside the `C:\venv\cragb` short-path venv**
(PLAN.md §14.1), not the base env.

**Validation checks:** every latency > 0 and `p50 <= p95`; `qps` consistent with
`1000 / latency_mean_ms` within rounding; `build_seconds` for both retrievers within a
sane factor of the T3.5 numbers already recorded (if not, record *why* in the run notes —
different machine state is a legitimate answer, silent drift is not); the same `k` as
`configs/retrieval_eval.yaml`, so these numbers describe the exact configuration whose
Recall@k is already reported.

**How I verify it worked:** `pytest tests/test_cost_latency_retrieval.py -q`; open the CSV
and check both rows; sanity-check `index_bytes` against the actual file sizes on disk.

**Git commit message:** `feat(eval): retrieval cost/latency harness — build time, size, QPS, p50/p95`

**Mid-progress report:** Yes — the retrieval half of the cost & latency table (§7).

## T5.4 — Pricing config + token accounting → $/query per arm

**Objective:** Turn token counts into money, with the price list treated as *data with a
date*, not a number buried in code. Groq's published per-million-token rates change and
models get deprecated mid-project (already happened once — PLAN.md §14.4).

**Artifact:**
- `configs/pricing.yaml` — per-model `input_usd_per_1m` / `output_usd_per_1m`, plus
  `snapshot_date` and `source_url` per entry, for `openai/gpt-oss-20b`,
  `openai/gpt-oss-120b`, and the T4b.4 judge model. Mirrors PLAN.md §14.4's
  catalog-snapshot discipline.
- `src/cragb/eval/cost_model.py` + `tests/test_cost_model.py` —
  `cost_usd(prompt_tokens, completion_tokens, model, pricing) -> float`,
  `arm_cost_table(call_rows, pricing) -> pd.DataFrame` (per-arm totals and per-query means
  with the CI helper M4b already uses, `cragb.eval.bootstrap.bootstrap_ci`).
- `results/tables/answer_cost_v1.csv` — per arm: `arm, model, n_questions,
  mean_prompt_tokens, mean_completion_tokens, mean_usd_per_query, usd_per_query_ci_lo,
  usd_per_query_ci_hi, total_usd, is_estimated`.

**Where the tokens come from:** the 180 T4b.2 transcripts predate T5.2's telemetry.
Re-issue each cached call through `complete_with_usage` (free — they are cache hits) so
the sidecar path fills in what it can; where usage is unrecoverable, fall back to a
documented estimate (`len(text) / 4` chars-per-token) and mark the row via `is_estimated`.
Do not silently mix measured and estimated numbers.

**Python packages:** `pandas`, `pyyaml` (present).

**Validation checks:** unit test against a hand-computed cost (e.g. 1,000 in + 500 out at
a known rate); `total_usd == mean_usd_per_query * n` within float tolerance; the
closed-book arm has **materially fewer prompt tokens** than the RAG arms (it sends no
context — if it doesn't, the arms got crossed); RAG-small and RAG-large have
near-identical prompt-token counts (same retriever, same k, same prompt — that's the RQ1
control, and this is a free check that it held).

**How I verify it worked:** `pytest tests/test_cost_model.py -q`; read the CSV and confirm
the 120B arm costs more per query than the 20B arm by roughly the published rate ratio.

**Git commit message:** `feat(eval): pricing config + token accounting -> $/query per arm`

**Mid-progress report:** Yes — the $/query column of the cost table (§7).

## T5.5 — End-to-end latency: live, cache-bypassed timed run per arm

**Objective:** The number a user would actually feel — retrieval + prompt build +
generation, per question, per arm. This is the one measurement that **cannot** come from
the cache, so it needs a deliberate live run on a subset.

**Artifact:**
- `src/cragb/eval/run_cost_latency.py` — CLI with an explicit `--no-cache` flag (bypass,
  never delete, the disk cache) and `--n-questions` (default: a fixed, seeded 15-question
  subset stratified across taxonomy types — not the first 15, since question type changes
  context length and therefore latency).
- `results/tables/e2e_latency_v1.csv` — per arm: `arm, model, n, retrieval_ms_p50,
  generate_ms_p50, e2e_ms_p50, e2e_ms_p95, e2e_ms_mean`, plus `run_timestamp` and a
  `cache_bypassed` boolean so the provenance of the timing travels with the data.
- `results/tables/e2e_latency_per_question_v1.csv` — the raw per-call rows.

**Expected outputs:** three arms × 15 questions = 45 live calls, each with a real latency;
closed-book should be fastest (no retrieval, short prompt).

**Python packages:** none new.

**Validation checks:** every row has `cached=False`; `e2e_ms >= retrieval_ms +
generate_ms` on every row (a violation means the timers overlap or double-count);
`p95 >= p50`; the run notes record network conditions and state plainly that this is a
single-client, sequential, **free-tier** measurement — Groq's shared free tier is not a
latency SLA, and the write-up must say so rather than presenting these as production
numbers.

**How I verify it worked:** the run takes real wall-clock time proportional to the
reported latencies — a run that finishes instantly means the cache bypass didn't work,
and that is the one failure mode worth staring at. Then confirm the cache behaved as
documented (45 new entries if bypass still writes through, zero if it doesn't — decide
which, and write it down).

**Git commit message:** `feat(eval): end-to-end latency harness (cache-bypassed live run)`

**Mid-progress report:** Yes — the latency column of the cost table (§7).

## T5.6 — Joined quality-vs-cost table + Pareto scatter (report figure #4)

**Objective:** The decision artefact. One table where each configuration is a row carrying
both its quality (from M4b) and its cost (T5.3–T5.5), plus the scatter that makes the
trade-off visible — PLAN.md §7 figure #4, §11 upgrade #5 ("the 70B is +6% quality at 12×
cost").

**Artifact:**
- `src/cragb/eval/pareto.py` + `tests/test_pareto.py` — `join_quality_cost(quality_df,
  cost_df, latency_df) -> pd.DataFrame` and `pareto_frontier(df, quality_col, cost_col)
  -> pd.Series[bool]` (marks non-dominated configurations).
- `results/tables/cost_quality_v1.csv` — one row per configuration (closed-book,
  RAG-small, RAG-large; BM25/dense retrieval rows carried under a `component` column):
  quality mean + CI, $/query, e2e p50 latency, `on_frontier`.
- `reports/figures/quality_vs_cost_pareto_v1.png` — x = $/query (log scale; the arms differ
  by an order of magnitude), y = judge quality (correctness or the composite),
  **error bars from M4b's bootstrap CIs**, frontier points connected, latency shown by
  point size or a second panel.

**Expected outputs:** a figure where the honest M4b result stays visible rather than
smoothed — RQ1's 20B-vs-120B quality gap is small with overlapping CIs
(`rq1_answer_quality_v1.csv`: correctness 3.67 vs 3.77, Wilcoxon p = 0.34), so the scatter
should show a large cost increase buying a quality difference that is **not statistically
distinguishable**. That is a finding, and the strongest available motivation for the
SLM/fine-tuning half of the project. Don't draw it in a way that implies a win the
statistics don't support.

**Python packages:** `matplotlib` (present), `pandas`, `numpy`.

**Validation checks:** unit test on `pareto_frontier` with a hand-built 4-point case
including a tie; every configuration in the quality tables appears exactly once in the
joined table (assert row counts before and after — no silent inner-join loss); the figure
renders with readable axis labels, units (`USD / query`), and a caption noting the pricing
snapshot date and that latencies are free-tier single-client.

**How I verify it worked:** `pytest tests/test_pareto.py -q`; open the PNG and check the
two RAG arms' CIs overlap, matching `rq1_answer_quality_v1.csv`.

**Git commit message:** `feat(eval): quality-vs-cost join + Pareto scatter (G4)`

**Mid-progress report:** **Yes — this is report figure #4 and one of the headline
artefacts of the whole first half.**

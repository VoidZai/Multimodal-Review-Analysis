# Milestone 6 — Multimodal grounding pilot (E7, Goal G3, RQ4)

**Status:** M1, M2, M3, M4a, M4b, M5 complete; M6 not started. This milestone covers
PLAN.md §3 E7 / §8 G3 / §2 RQ4 — measuring whether the photo the pipeline surfaces
alongside an answer is *actually relevant evidence*, honestly scoped to the image-bearing
subset. It is the second half of Component 2 ("multimodal retrieval & evidence
grounding") and the direct mitigation for PLAN.md §1.4 **risk D** (the "visual grounding"
over-claim).

**The claim this milestone is allowed to make:** *evidence surfacing*, not image-conditioned
generation. The text generator never sees pixels — it sees `has_photo: yes/no` flags in the
context block (confirmed in `results/tables/answer_gen_rag_small_v1.jsonl`'s
`context_photo_flags`). RQ4 asks whether the photo a user would be shown next to the
answer beats a random photo from the same corpus, judged pairwise by a vision LLM. Any
sentence in the report implying the model *reasoned over* the image is false and must not
be written.

**Scope in:** fetching and caching the actual image bytes; a Gemini multimodal client
behind the project's existing cache/telemetry discipline; assembling
(question, surfaced-photo, random-control-photo) triples from the *pipeline's own*
retrieval output; a position-bias-controlled pairwise vision judge; win-rate with
bootstrap 95% CI and a significance test against the 0.5 null; coverage accounting;
a human spot-check of the vision judge; report figure #6, appendix examples, and
notebook `09_multimodal_pilot.ipynb`.

**Scope out:** fine-tuning data prep (M7); any change to the retriever, the grounded-QA
prompt, or the text answer-quality judge; image-conditioned *generation* (explicitly
ruled out by PLAN.md §12 and risk D); training or fine-tuning any vision model.

---

### Four facts about the current state that shape this milestone

1. **There is no vision model on Groq.** PLAN.md §14.4's live catalog snapshot
   (2026-08-19) lists 13 models — `gpt-oss-{20b,120b}`, `qwen3.6-27b`, two compound
   agentic systems, two prompt-guard classifiers, TTS and Whisper. None accept image
   input. M6 therefore introduces the **second free-tier provider PLAN.md §1.3 already
   named — Google AI Studio (Gemini)** — as a new client (T6.2). This is an additive
   provider, not a replacement: every existing Groq-backed result stays exactly as it is.

2. **`GroqClient` types messages as `list[dict[str, str]]`.** A multimodal message body is
   `{"role": "user", "content": [ {text part}, {image part} ]}` — a list, not a string.
   The new client must express that shape; the Groq client's signature must not be
   loosened just to accommodate it (nothing in M1–M5 needs it, and widening the type
   invites a caller to send an image to a text-only model and get a confusing 400).

3. **The corpus holds image URLs, not image bytes.** `corpus_v1.parquet` has
   `image_urls` (external `m.media-amazon.com` CDN links) for 30,000 of 200,000 rows;
   `data/processed/corpus_v1_datasheet.md` flags this explicitly. Those links are outside
   our control and may 404 or rate-limit. Bytes must be fetched once, content-addressed on
   disk, and a fetch-failure treated as a *reportable coverage loss*, not a crash.

4. **The image-bearing subset is small and already known — plan the power accordingly.**
   `cragb_v1.jsonl`: 60 questions, **49 `image_target: true`**, and
   `benchmark/best_photo_v1.jsonl` finds a human best-evidence photo for only **37** of
   them (12 image-target questions have no image-bearing *relevant* review at all). The
   pipeline-surfaced subset will be its own number, ≤49, computed in T6.3. At n≈35–45
   paired judgments, a true win-rate of 0.75 is comfortably distinguishable from 0.5 but
   a win-rate of 0.60 is not — PLAN.md §3 E7's "too few image-bearing questions →
   underpowered" failure mode is live, so T6.5 must report the CI honestly rather than
   claiming significance it does not have.

**Ordering:** T6.1 and T6.2 are independent and can be built in either order. T6.3 needs
T6.1. T6.4 needs T6.2. T6.5 needs everything before it. T6.6–T6.7 are reporting.

Code is not written yet; this file is the task breakdown only.

## T6.1 — Photo byte store: fetch, content-address, cache, report coverage

**Objective:** Turn `image_urls` (external CDN links) into locally-cached image bytes the
vision judge can actually send, exactly once, with every fetch failure recorded rather
than swallowed. This is the module that decides how many questions RQ4 can speak about,
so its coverage output is a *result*, not a log line.

**Artifact:**
- `src/cragb/multimodal/photo_store.py` —
  - `photo_id(url) -> str` — a stable content-address (sha256 of the URL, first 16 hex
    chars) used as the on-disk filename, so the same URL never downloads twice and the
    id is reproducible across machines without a shared database.
  - `fetch_photo(url, *, force=False) -> PhotoRecord(photo_id, url, path, bytes_len, mime, width, height, status)` —
    reuses `download.py`'s `_build_session` retry/backoff pattern (same discipline as
    T1.2); `status` is one of `ok | http_error | timeout | not_an_image | too_large`.
  - `fetch_many(urls) -> list[PhotoRecord]` with a polite fixed inter-request delay (do
    not hammer Amazon's CDN) and a hard per-image size cap from config.
  - `load_photo_bytes(photo_id) -> bytes` and `to_data_part(photo_id) -> dict` — the
    base64 inline-data part shape T6.2's client expects.
- `data/photos/` — the byte cache (add to `.gitignore` alongside `results/cache/`).
- `data/photos/manifest_v1.json` — **committed** (like `corpus_v1_manifest.json`): one row
  per attempted URL with `photo_id`, `url`, `status`, `bytes_len`, `mime`, `width`,
  `height`, plus a summary block (`n_attempted`, `n_ok`, `n_failed_by_status`). This is
  what makes the pilot reproducible when a CDN link dies six months from now.
- `configs/photo_store.yaml` — `photos_dir`, `max_bytes`, `timeout_s`, `max_retries`,
  `request_delay_s`, `allowed_mime`.
- `tests/test_photo_store.py`.

**Expected outputs:** `python -m cragb.multimodal.photo_store fetch` populates
`data/photos/` and writes the manifest; a printed coverage summary of the form
`attempted N, ok M (X%), failed by status {...}`.

**Python packages:** `requests` (already used by `download.py`), `Pillow` (decode +
`width/height` + a real "is this actually an image" check — a 404 HTML page returned with
status 200 must be caught as `not_an_image`, not base64'd into a judge prompt),
`hashlib`/`base64` (stdlib).

**Validation checks:** unit tests with a mocked/stubbed HTTP session — a 200 + valid JPEG
gives `status="ok"` and a file on disk; a 404 gives `status="http_error"` and **no** file
written; an HTML body returned as 200 gives `not_an_image`; a body over `max_bytes` gives
`too_large` without buffering the whole thing into memory; `photo_id` is deterministic for
the same URL and differs for different URLs; calling `fetch_photo` twice hits the cache
(assert exactly one HTTP call). Separately assert the manifest's `n_ok` equals the number
of files actually present in `photos_dir` — a manifest that disagrees with the disk is
worse than no manifest.

**How I verify it worked:** `pytest tests/test_photo_store.py -q` passes; then run the
real fetch over the image-target questions' candidate URLs and confirm the printed
`n_ok` ≥ 30 (below that, RQ4 is underpowered and I stop to reconsider before spending
judge calls); open two or three cached files and confirm they are genuinely photographs of
clothing.

**Git commit message:** `feat(mm): content-addressed photo byte store + coverage manifest (E7)`

**Mid-progress report:** **Yes** — the image-coverage numbers go straight into the honest
coverage paragraph RQ4 requires (PLAN.md §7's "image coverage %"), and the manifest is
appendix-grade reproducibility evidence.

**Estimate:** 60–75 min.

## T6.2 — Gemini multimodal client (second provider, same cache/telemetry discipline)

**Objective:** Add the one capability the project does not have — sending an image to an
LLM — without breaking any of the five milestones already built on Groq, and without
losing the token/latency telemetry M5 spent a whole milestone establishing.

**Artifact:**
- `src/cragb/generate/gemini_client.py` — `GeminiClient`, a dataclass mirroring
  `GroqClient`'s field shape (`model`, `api_base`, `api_key_env="GOOGLE_API_KEY"`,
  `temperature`, `max_tokens`, `timeout_s`, `max_retries`, `cache_dir`, `call_log_path`)
  and exposing the **same two methods**: `complete(parts) -> str` and
  `complete_with_usage(parts) -> CompletionResult`. Reuses `CompletionResult` and
  `DiskCache` unchanged, and appends to the same `results/cache/api_calls_v1.jsonl`, so
  T5.4's cost accounting reads M6's calls for free.
  - Message shape: a `list` of parts — `{"type": "text", "text": ...}` and
    `{"type": "image", "photo_id": ..., "mime": ..., "data_b64": ...}` — translated inside
    the client into Gemini's `contents[].parts[]` `inline_data` format. Keeping the
    project-side shape provider-neutral means the vision-judge module (T6.4) never
    imports a Gemini-specific dict.
  - Token counts come from the response's `usageMetadata`
    (`promptTokenCount` / `candidatesTokenCount`) mapped onto `CompletionResult`'s
    existing `prompt_tokens` / `completion_tokens` fields.
  - `bypass_cache` flag, same semantics as T5.5's (skip both read and write) so a latency
    measurement is never a cache hit.
- `.env.example` — add `GOOGLE_API_KEY=` with the console URL and a one-line note on what
  uses it.
- `configs/vision_judge.yaml` — provider block written here (model id, temperature 0.0,
  `max_tokens`, `api_base`); the prompt/rubric half is added in T6.4.
- `tests/test_gemini_client.py`.

**Expected outputs:** module importable with no key set (key read lazily per call, exactly
as `GroqClient._api_key` does); a fake-transport test showing a live call records tokens +
latency and a repeat of the same call reports `cached=True`.

**Python packages:** `requests` only — do **not** add the `google-generativeai` SDK. Same
reasoning as T2.2's rejection of the `groq` SDK: one call shape does not justify a new
dependency tree, and the REST body is stable and easy to test with a stubbed session.

**Validation checks:** the **Groq cache is untouched** — assert that constructing and
using `GeminiClient` writes only under its own cache namespace and that a known
`GroqClient` payload's cache key is byte-identical to before this task (the same
regression guard T5.2 used; a silent key change re-spends free-tier quota); the cache key
for a multimodal payload includes the image bytes' digest, so swapping the image with the
same text is a cache **miss** (otherwise the A/B-swap runs in T6.4 would collude and
return each other's answers); a missing `GOOGLE_API_KEY` raises the same
`MissingAPIKeyError` with an actionable message rather than a bare `KeyError`; a response
with no `usageMetadata` yields `None` token counts rather than crashing (the M5 §14.5
lesson, applied on day one this time).

**How I verify it worked:** `pytest tests/test_gemini_client.py -q` passes; then one live
smoke call sending a real cached photo from T6.1 plus "Describe this image in one
sentence" and confirm the description actually matches the picture — this is the single
check that proves image bytes are reaching the model rather than being silently dropped
(a text-only fallback still returns fluent, plausible, useless text).

**Git commit message:** `feat(generate): Gemini multimodal client with usage telemetry (E7)`

**Mid-progress report:** Indirect (infrastructure) — but the "two free-tier providers,
one cache/telemetry interface" point is worth one sentence in the engineering section.

**Estimate:** 75–90 min.

## T6.3 — Photo linking: surfaced vs random-control pairs, with coverage accounting

**Objective:** Build the pilot's actual experimental units. For each image-target question,
resolve **the photo the pipeline itself would surface** (measuring the system as built, not
the benchmark's oracle) and a **seeded random control photo**, and account for every
question that drops out and why.

**Artifact:**
- `src/cragb/multimodal/photo_link.py` (the module PLAN.md §5 already names) —
  - `surfaced_photo(question_id) -> str | None` — walk that question's RAG-small
    transcript (`results/tables/answer_gen_rag_small_v1.jsonl`) in retrieved-rank order,
    take the **first retrieved doc with `context_photo_flags[doc_id] == True`**, and
    return its first image URL's `photo_id`. Rank order, not the cited set: the
    transcripts inspected in `reports/grounded_qa_transcripts_v1.md` show the model
    under-uses `[photo of ...]` citations even when the prompt offers them
    (`cited_photo_ids` is empty in the sampled rows), so keying on citations would
    collapse the sample to near-zero.
  - `control_photo(question_id, rng) -> str` — a photo sampled from the image-bearing
    corpus **excluding that question's `relevant_ids` and excluding every doc in its
    retrieved context**, so the control cannot accidentally be genuinely relevant. Seeded
    from `configs`' `seed: 42` via `utils/seeds.py`, so the control set is reproducible.
  - `build_pairs() -> pd.DataFrame` — one row per usable question:
    `question_id, type, question, surfaced_photo_id, surfaced_doc_id, control_photo_id,
    control_doc_id, drop_reason`.
- `results/tables/mm_pairs_v1.jsonl` — the pair set actually judged.
- `results/tables/mm_coverage_v1.csv` — the coverage funnel, one row per stage:
  `60 total → 49 image_target → N with a photo-bearing retrieved doc → M with fetchable
  bytes (T6.1) → K judged`, with the drop reason for each stage. This table is the honest
  answer to "what fraction of questions can this feature even fire on."
- `configs/multimodal.yaml` — paths, seed, `top_k` scan depth, control-sampling rules.
- `tests/test_photo_link.py`.

**Expected outputs:** the two result files plus a printed funnel; `K` is stated explicitly
before any judge call is spent.

**Python packages:** `pandas`, `numpy` (both already project dependencies).

**Validation checks:** the control photo is never drawn from the question's `relevant_ids`
nor from its retrieved context (assert over the whole generated set, not one example — this
is the check that keeps the "control" a control); the same seed reproduces byte-identical
controls across two runs; a question whose retrieved docs have no photo produces a row with
`drop_reason` set and **no** silent omission; the funnel's stage counts are monotonically
non-increasing and the final stage equals `len(mm_pairs_v1.jsonl)` (the M2 §14.3 lesson —
an invariant that is never asserted quietly stops being true).

**How I verify it worked:** `pytest tests/test_photo_link.py -q`; then eyeball three rows —
open the surfaced photo and the control side by side against the question text and confirm
the pairing is sane and the control looks unrelated.

**Git commit message:** `feat(mm): surfaced-vs-control photo pairing + coverage funnel (RQ4)`

**Mid-progress report:** **Yes** — the coverage funnel is a table in its own right and is
the honest framing PLAN.md §3 E7 demands.

**Estimate:** 75–90 min.

## T6.4 — Pairwise vision judge (prompt + parser + position-bias control)

**Objective:** The G3 instrument itself: given the question and two photos, which is the
better *evidence* for answering it? Built with the same rigor as T4b.4's text judge —
deterministic, strictly parsed, and with the one bias that matters for pairwise designs
(position/order preference) controlled by construction rather than hoped away.

**Artifact:**
- `src/cragb/generate/prompts/vision_judge_v1.md` — versioned prompt: states the task is
  **evidence relevance for this specific question**, not photo aesthetics or image quality;
  presents Photo A and Photo B; demands a single JSON object
  `{"winner": "A"|"B"|"tie", "confidence": 1-5, "rationale": "<= 30 words"}`; forbids
  prose outside the JSON.
- `src/cragb/multimodal/vision_judge.py` —
  - `build_vision_prompt(question, photo_a, photo_b) -> list[parts]` using T6.2's
    provider-neutral part shape.
  - `parse_vision_response(raw) -> VisionVerdict(winner, confidence, rationale)` — strict
    single-JSON-object parsing, with the same `<think>`-stripping defensiveness T4b.4
    needed (PLAN.md §14.4); an unparseable response raises a typed error rather than
    defaulting to a winner (a judge that silently defaults to "A" manufactures exactly the
    result we are testing for).
  - `judge_pair(question, surfaced_id, control_id) -> PairVerdict` — runs **both orders**
    (surfaced-as-A and surfaced-as-B) and returns both verdicts plus
    `order_agreement: bool`. A pair counts as a surfaced-photo *win* only if surfaced wins
    in both orders; disagreement between orders is recorded as a tie and reported as the
    position-bias diagnostic.
- `configs/vision_judge.yaml` — completed with `prompt_template`, `orders: both`,
  `temperature: 0.0`, tie handling.
- `tests/test_vision_judge.py`.

**Expected outputs:** module importable; parser unit-tested against real-shaped strings;
no network needed for any test.

**Python packages:** none new.

**Validation checks:** parser accepts a bare JSON object, a fenced json code block, and a
`<think>…</think>`-prefixed response; rejects two JSON objects, prose-only, and a missing
`winner` key — each with a typed error; `judge_pair` issues exactly **two** calls with the
photo positions genuinely swapped (assert on the recorded payloads, not just the call
count); a stubbed judge that always answers "A" yields `order_agreement=False` and a tie
for every pair — the sanity check proving the design actually detects position bias rather
than laundering it into a 100% win-rate.

**How I verify it worked:** `pytest tests/test_vision_judge.py -q`; then run the judge live
on **three** hand-picked pairs where I already know which photo is more relevant and
confirm it agrees, before committing quota to the full run.

**Git commit message:** `feat(mm): pairwise vision-evidence judge with order-swap control (G3)`

**Mid-progress report:** **Yes** — the versioned prompt is one of the four prompt examples
PLAN.md §7 requires in the appendix ("pairwise vision-judge prompt").

**Estimate:** 75–90 min.

## T6.5 — Run the pilot: win-rate, bootstrap CI, significance vs the 0.5 null

**Objective:** Execute E7 end to end and turn K pair verdicts into the RQ4 result table,
with the uncertainty stated honestly at this sample size.

**Artifact:**
- `src/cragb/eval/run_multimodal_pilot.py` — orchestrator: load pairs (T6.3) → judge both
  orders (T6.4) → write per-pair rows → aggregate.
- `results/tables/mm_verdicts_v1.jsonl` — one row per pair: both verdicts, confidences,
  rationales, `order_agreement`, `outcome ∈ {surfaced_win, control_win, tie}`, token counts
  and latency (free, via T6.2's telemetry).
- `results/tables/mm_winrate_v1.csv` — headline: `n_pairs`, `win_rate`, `ci_lo`, `ci_hi`,
  `p_value` vs the 0.5 null, `tie_rate`, `order_agreement_rate`, plus a **per-question-type
  breakdown** (fit_sizing / colour_appearance / defects / … — H4 predicts photos help most
  on `colour_appearance` and `defects`, and that split is more interesting than the pooled
  number).
- `results/tables/mm_cost_v1.csv` — judge calls, tokens, $ and wall-clock for the run,
  reusing `eval/cost_model.py`; keeps M5's G4 accounting complete across all providers.
- `tests/test_run_multimodal_pilot.py`.

**Expected outputs:** the three result files; a printed one-line summary
`win-rate X.XX [lo, hi], n=K, p=…, ties=…, order-agreement=…`.

**Python packages:** `numpy`, `pandas`, `scipy` (binomial test against 0.5 —
`scipy.stats.binomtest`); reuse `eval/bootstrap.py`'s `bootstrap_ci` for the CI so the M6
interval is computed the same way as every M3/M4b interval.

**Validation checks:** win-rate computed on a hand-built fixture of known verdicts equals
the hand-computed value; ties are excluded from the numerator but **included in the
denominator** (and the CSV says which convention was used — the single most common way a
pairwise win-rate gets quietly inflated); the CI brackets the point estimate; with a
stubbed all-tie verdict set the win-rate is 0.0 and the p-value is not significant;
`n_pairs` in the CSV equals the row count in `mm_verdicts_v1.jsonl` equals the funnel's
final stage from T6.3. Run with a stub judge in tests — **zero** network calls in `pytest`.

**How I verify it worked:** `pytest tests/test_run_multimodal_pilot.py -q`; then the live
run — check `results/cache/api_calls_v1.jsonl` grew by exactly `2 × n_pairs` rows, and
sanity-read five rationales to confirm the judge is reasoning about evidence relevance and
not about photo prettiness. **If the CI includes 0.5, I report that** as an underpowered
null result with the coverage funnel as the explanation; I do not go fishing for a subgroup
that clears significance.

**Git commit message:** `feat(mm): RQ4 pilot run — photo-evidence win-rate + CI (E7, G3)`

**Mid-progress report:** **Yes — this is the RQ4 headline number.**

**Estimate:** 75–90 min (plus live-run wall clock; budget for free-tier 429s per PLAN.md
§1.4 bottleneck #3 — M5's 45-call run took ~5.5 real minutes, and this is roughly 2× that).
